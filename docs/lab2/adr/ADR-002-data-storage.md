# ADR-002: PostgreSQL и Prisma ORM для хранения данных

**Статус:** Принято

**Контекст.** Данные сервиса сильно связаны: пользователь → члены семьи → аллергены; блюдо → ингредиенты → аллергены; рацион → приёмы пищи → блюда; ингредиент → товары сетей. Почти каждый запрос проходит по нескольким связям. Чтобы исключить блюдо (FR-03), нужно дойти от члена семьи до аллергенов ингредиентов. Для списка покупок (FR-09) нужно собрать ингредиенты всех блюд рациона, для корзины (FR-13) — сопоставить их с товарами пяти сетей. FR-01.4 требует, чтобы рационы и списки были доступны с любого устройства, поэтому хранить их только в браузере нельзя. NFR-02 ограничивает генерацию рациона 5 секундами на каталоге из 500 блюд. Цены и количества должны считаться без ошибок округления (FR-12, FR-13, FR-15).

**Рассмотренные альтернативы.**

1. *MongoDB*. Отклонена: документная модель хорошо ложится на «рацион целиком», но плохо — на справочники, которые используются многими рационами (блюда, ингредиенты, цены). Пришлось бы либо денормализовать и следить за копиями, либо делать связи вручную через `$lookup`. Целостность ссылок (блюдо в рационе существует, аллерген известен) база бы не гарантировала.
2. *SQLite*. Отклонена: для прототипа её хватило бы, но в ЛР 1 заложены несколько одновременных пользователей (NFR-04) и регулярное фоновое обновление цен (NFR-03). При записи SQLite блокирует файл целиком, и переход на серверную СУБД всё равно понадобился бы.
3. *TypeORM вместо Prisma*. Отклонён: сущности на декораторах и схема в классах удобны, но Prisma даёт один декларативный файл `schema.prisma`. Из него генерируются и миграции, и типизированный клиент, и по нему же рисуется ER-диаграмма. Типы результатов с `include` выводятся автоматически, и для вложенных выборок (рацион → блюда → ингредиенты → аллергены) это заметно сокращает код.

**Принятое решение.** Используем PostgreSQL 17 (в Docker Compose для разработки) и Prisma ORM 7 с драйвер-адаптером `@prisma/adapter-pg`. Схема описана в `app/backend/prisma/schema.prisma` и меняется только миграциями Prisma Migrate. Ключи пользовательских сущностей — UUID, справочников — автоинкремент. Связующие таблицы (`MemberAllergen`, `DishIngredient`, `ShoppingMark` и др.) используют составные первичные ключи. Деньги и количества хранятся как `decimal` и переводятся в `number` на границе сервиса. Производные данные в базу не пишутся: список покупок и корзины вычисляются из рациона и цен при каждом запросе, хранятся только пользовательские отметки «куплено» и «есть дома». Один экземпляр `PrismaClient` живёт в глобальном `PrismaModule`.

**Последствия.**

- *Упрощается:* целостность обеспечивает сама база — внешние ключи, уникальность пары «сеть — ингредиент», каскадное удаление рациона вместе с приёмами пищи и отметками. Типы запросов проверяет компилятор: ошибка в имени поля или связи не соберётся. Список и корзина всегда соответствуют текущему рациону, синхронизировать нечего (FR-07.3).
- *Усложняется:* после каждого изменения схемы нужна миграция и повторная генерация клиента (`postinstall` делает это автоматически). Для разработки нужен работающий Postgres, поэтому в репозитории есть `docker-compose.yml`. Вычисление списка «на лету» означает, что каждый запрос корзины заново читает рацион с ингредиентами.
- *Риски:* Prisma 7 вышла недавно и требует драйвер-адаптер и `prisma.config.ts`. Многие примеры в интернете написаны под шестую версию и уже не подходят. При каталоге в 500 блюд и рационе на 31 день вычисляемый список может упереться в NFR-04. Тогда его нужно кэшировать и сбрасывать при замене блюда, а схему для этого менять не придётся.

**Роль агента.** PostgreSQL выбрала команда, когда отвечала на вопрос агента о стеке. Агент предложил Prisma вместо TypeORM, аргументировав это тем, что `schema.prisma` сразу служит источником для ER-диаграммы. Агент обнаружил, что установленная версия Prisma (7.10) новее его знаний. Конфигурацию он писал не по памяти, а по справке, которую `prisma init` положил в проект: прочитал её и затем удалил из репозитория вместе с другими сгенерированными файлами агентов. Хранить список покупок вычисляемым, а не отдельной таблицей, предложил агент, чтобы выполнить FR-07.3 без синхронизации. Сбросить базу через `prisma migrate reset` агент не смог: Prisma блокирует эту команду для ИИ-агентов без явного согласия пользователя. Поэтому сид переписан так, что каталог создаётся один раз, а цены обновляются при каждом запуске.
