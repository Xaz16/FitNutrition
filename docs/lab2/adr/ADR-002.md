# ADR-002: Серверная SQLite и снимок настроек плана

## Статус

Принято

## Контекст

FR-01 требует сохранить данные учётной записи; FR-10 — запасы после повторного входа; FR-05 и FR-07 — целостное меню и замену одной позиции. Нельзя записать половину нового плана и потерять предыдущий при нехватке рецептов.

## Рассмотренные альтернативы

1. PostgreSQL: подходит для многопользовательского развёртывания, но отдельный сервер и настройка избыточны для локальной защиты.
2. JSON-файл: прозрачен, но потребовал бы ручной координации одновременных записей, уникальности и связей.
3. localStorage: удобен для черновиков UI, но привязан к конкретному браузерному профилю и не выполняет серверную часть FR-01.

## Принятое решение

Использовать SQLite через sqlite3. Включать foreign_keys на каждом соединении, передавать значения через SQL-параметры, закрывать соединения явно. Записывать план и позиции одной транзакцией; сначала полностью рассчитывать допустимое меню в памяти. Сохранять settings_json в плане, чтобы последующие изменения формы не меняли трактовку уже созданного периода. Состав фиксированного рецепта пока хранится в JSON.

## Последствия

Упрощаются резервное копирование и запуск. Усложняются конкурентная запись при росте нагрузки и запросы по JSON-составу. Риск нарушения ссылок внутри JSON ограничен фиксированным каталогом, но не устранён SQL. Перед редактированием каталога нужны нормализация recipe_ingredients и миграции; дальнейшая база не обещана неизменной.

## Роль агента

Агент сформировал ER по фактической схеме, отметил ограничение JSON и добавил API-проверку сохранения предыдущего плана. Тест на Windows обнаружил, что контекст SQLite сам по себе не закрывал соединение; агент ввёл явное закрытие. Пользователь не заявлял эти проверки как выполненные им лично.
