# ADR-001: Модульный монолит с браузерным интерфейсом

## Статус

Принято

## Контекст

FR-05–15 связывают меню, список и стоимость. Изменение блюда должно согласованно пересчитывать производные данные. FR-01 требует входа и сохранения данных пользователя, NFR-05 — браузерного интерфейса на нескольких ширинах. Команде нужен запускаемый срез без отдельной инфраструктуры для каждого компонента.

## Рассмотренные альтернативы

1. Микросервисы: дают независимое развёртывание, но для первого среза добавляют сетевые отказы, отдельные конфигурации и сложность транзакций.
2. Полностью клиентское приложение: проще запуск, однако хранение только в браузере не обеспечивает данные учётной записи при входе из другой сессии на сервере.
3. Desktop-приложение: удобно локально, но требует упаковки под платформы и расходится с браузерным направлением исходной презентации.

## Принятое решение

Один Python-процесс отдаёт статический HTML/CSS/JavaScript и HTTP API. Вычисления вынесены в domain.py, источник цен — в prices.py; транспорт и SQL пока находятся в server.py. В браузере нет второго независимого механизма расчёта корзины: он отображает согласованный снимок сервера.

## Последствия

Упрощаются запуск, отладка и транзакционная запись плана. Усложняется дальнейшее выделение авторизации и хранения из HTTP-обработчика. Риск — рост server.py при добавлении функций; границы уже заданы контрактами. Стандартный HTTP-сервер годится для локальной демонстрации, но требует замены или production-обвязки при публикации.

## Роль агента

Агент предложил серверное хранение после проверки FR-01 сданной ЛР1 и выбрал небольшой модульный монолит. Пользователь подтвердил набор экранов до программирования и уточнил аудиторию. Выбор конкретной серверной реализации выполнен агентом в рамках порученной разработки; отдельное сравнение технологий пользователем не приписывается.
