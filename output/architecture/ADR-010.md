# ADR-010: Повторная проверка аллергенов при замене

## Статус

Принято. Уточнение архитектуры действующего прототипа от 26.10.2026.

## Контекст

FR-03 задаёт исключения, FR-07 требует допустимую замену. Пользователь может открыть окно вариантов, затем изменить профиль или план в другом окне. Каталог содержит метки аллергенов ингредиентов.

## Проблема

Фильтра только в интерфейсе недостаточно: клиент может отправить произвольный recipe_id, а открытый список может устареть.

## Рассмотренные альтернативы

Клиентская проверка даёт быстрый отклик, но не является границей правил. Проверка только при GET не защищает последующий POST. Снятие ограничений при отсутствии вариантов противоречит потребности пользователя.

## Принятое решение

Использовать общий replacement_candidates для GET /api/alternatives и повторно для POST /api/replace. allowed проверяет каждый ингредиент: пересечение его аллергенов с запретами должно быть пустым, исключённые продукты запрещены. Также учитываются предпочтения, время, тип приёма, повторы и диапазон калорий ±15% до подстройки порции. POST проверяет владельца, отпечаток профиля и revision в транзакции. При нарушении возвращается ошибка без записи.

## Последствия

Предварительный список и применение подчиняются одним правилам. При отсутствии вариантов ограничения сохраняются. Корректность зависит от полноты меток фиксированного каталога: следы аллергенов и производственные загрязнения не моделируются. Неопознанный текст из «Других аллергий» блокирует генерацию до уточнения, а не игнорируется.

## Роль агента

Агент сопоставил решение с allowed, plan_settings и обработчиком замены, отметил зависимость от данных каталога. В этой итерации подготовлены документы и схемы без изменения фильтра и запуска тестов.
