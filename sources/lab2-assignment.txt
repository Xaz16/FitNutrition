Лабораторная работа 2. Архитектура и
интерактивный прототип в коде
Цель: спроектировать архитектуру и создать работающий интерактивный прототип в
коде (с графическим интерфейсом, экранными формами и навигацией по ключевым
сценариям) с использованием ИИ-агента для генерации кода и диаграмм.
Репозиторий и коммиты:
Все документы и код курса ведутся в одном репозитории (Git) на протяжении всех
лабораторных работ.
Репозиторий не обязательно публичный — допустим локальный, но обязательно с
сохранением истории изменений.
После выполнения лабораторной работы сделайте как минимум один коммит:
архитектурный документ, диаграммы, отчёт о работе с агентом и код прототипа.
Содержание:
1. Структурная схема системы — верхнеуровневое представление состава подсистем и
модулей, их ответственности.
2. Технологический стек — язык, фреймворки для UI, БД и т.д. — просто перечислить
3. Диаграммы UML:
диаграмма вариантов использования (use case);
диаграммы активности:
Для одного студента — только основной сценарий использования (один
flow).
Для команды — три диаграммы активности: основной, альтернативный и
сценарий обработки исключительной ситуации (например, ошибка
валидации, отказ внешнего сервиса).
4. ER-диаграмма (модель данных) с указанием атрибутов, первичных ключей и связей.
5. Описание программных интерфейсов взаимодействия компонент — контракты,
форматы данных, сигнатуры основных методов/API.
6. Для команды: Предварительная отрисовка wireframe-ов экранных форм. Вы должны
согласовать UI в команде до начала программирования.
7. Создание интерактивного прототипа в коде с участием ИИ-агента:
Реализуются экранные формы (окна/страницы) с возможностью перехода между
ними по ключевым сценариям (навигация).
Код генерируется с помощью агента (например, Open Code, Cursor, Copilot, Claude
Code) — студенты фиксируют, как ставили задачи агенту, какие корректировки
вносили.
Прототип должен быть исполнимым — запускаться и демонстрировать
интерфейс.
8. Документирование архитектурных решений (ADR) — ADR для ключевых решений
(выбор архитектурного стиля, способа хранения данных, взаимодействия слоёв и т.д.).
В ADR обязательно отражается, какую роль сыграл агент в формировании решения.
Для одного студента — 3 ADR.
Для команды — 5 ADR.
Каждый ADR должен строго следовать приведённой ниже структуре:
Раздел

Краткое, ёмкое название решения. Формат:

решения (например, ADR-001: Выбор React + TypeScript в качестве

ADR-002: Выбор базы данных
Статус: Принято
Контекст: Система управления задачами должна хранить данные о пользователях,
проектах и задачах. Требование FR-12: поддержка поиска задач по тексту. Требование
NFR-03: время ответа API не более 200 мс при 1000 задач.
Рассмотренные альтернативы:
1. PostgreSQL — мощный, но сложный в настройке полнотекстового поиска.
2. MongoDB — гибкая схема, но слабый поиск.
3. SQLite — простота, но плохая масштабируемость.
Принятое решение: Используем PostgreSQL с расширением pg_trgm для
полнотекстового поиска. Данные реляционные, что соответствует предметной
области.
Последствия:
Упрощается: целостность данных, сложные запросы с JOIN.
Усложняется: требуются миграции при изменении схемы.
Риски: при росте потребуется индексация и настройка производительности.
Роль агента: Агент предложил три варианта (PostgreSQL, MongoDB, Redis) и сравнил их
по скорости поиска. Мы попросили агента учесть требование по текстовому поиску,
после чего он рекомендовал PostgreSQL. Самостоятельно мы добавили уточнение про
расширение pg_trgm, так как агент не знал о нём.
Результат лабораторной работы:
Архитектурный документ (структурная схема, UML-диаграммы, ER-диаграмма,
описание интерфейсов, ADR).
Wireframe-ы (только для пар).
Интерактивный прототип в коде (исходный код, запускаемый) с навигацией между
экранными формами.
Отчёт о работе с агентом при создании прототипа и диаграмм.
Критерии оценки:
Обоснованность архитектурных решений, полнота и качество ADR.
Корректность и полнота структурной схемы, UML- и ER-диаграмм (для пары —
большее количество диаграмм активности).
Качество описания программных интерфейсов.
Качество wireframe-ов (для пар): соответствие требованиям и сценариям.
Работоспособность интерактивного прототипа, удобство навигации, соответствие
требованиям из ЛР 1.
Качество использования агента: зафиксированные промпты, анализ предложений
агента, внесённые корректировки (отражается в отчёте или ADR).
Качество оформления ADR: полнота заполнения всех разделов (особенно
«Последствия» и «Роль агента»), обоснованность выбора, чёткая связь с требованиями
из ЛР 1. ADR должны быть согласованы с UML-диаграммами и структурной схемой
системы.

сохранена, есть коммит по итогам работы
